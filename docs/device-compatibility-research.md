# MINI_KEYBOARD 모델·프로토콜 호환성 조사

2026-10-24. **새 65바이트 계열과 구형 FD50 계열은 다른 코덱이어야 한다. VID:PID만으로 선택하면 안 된다.** 같은 `514c:8850`에서 현재 프로젝트의 16키/3노브와 공개 프로젝트의 3키/1노브가 서로 다른 레코드 형식을 사용한다. 모델 카탈로그·장치 검색·읽기 성공·설정 쓰기/복원 검증을 각각 구분해야 한다.

이 조사에서 하드웨어 명령을 보내지 않았다. REA 활성 타깃은 다른 작업이 소유하므로 변경하지 않았다. REA 네이티브 엔진이 준비되지 않은 상태에서 기존 `otool` 어셈블리를 수동 해석했다. 아래 주소는 디컴파일 결과가 아니라 정적 명령 해석이다.

## 검색 목록은 지원 검증표가 아니다

`nm`와 `otool -s __DATA __data`로 확인한 `_VID @0x10022d6b0 = 0x1189`, `_PID @0x10022d6b2 = 0x8840`, `_PID_GRU @0x10022d6c0`의 순서는 `8842,8840,8830,8831,8832,8833,8850,8851`이다. `0x100036445–0x100036479`에는 VID `514c`로 탐색하는 경로도 있다. 이는 업체 앱의 탐색 후보이며 모든 조합의 동작 검증을 뜻하지 않는다.

권장 카탈로그는 `mini3x1`, `mini6x1`, `mini6x2`, `mini9x2`, `mini12x2`, `mini12x3`, `mini12x4`를 **미검증 레이아웃 후보**로 구분한다. 원본 `Set_Keyboard_Ver()`에는 `3+1KEY @0x10003c48e`, `6+1KEY @0x10003c67e`, `6+2KEY @0x10003c6e4`, `9+2KEY @0x10003c74a`, `12+2KEY @0x10003c86f`, `12+3KEY @0x10003c8d2` 문자열이 있다. 이 문자열은 물리 배치나 현재 연결 장치의 프로토콜 증거가 아니다. `12+4KEY` 문자열은 찾지 못했으며 12+4 매핑은 아래 공개 소스로만 뒷받침한다.

## 두 업체 앱 경로의 정확한 구분

아래 `wire[n]`는 hidapi의 report ID를 포함한 65바이트 버퍼 인덱스다. `rec[n]`는 report ID 뒤에 붙는 저장 레코드의 인덱스다. WebHID에서는 report ID를 별도로 넘기므로 `wire[n] = payload[n-1]`이다.

`Read_KeyBoard_KeyNum() @0x10003de10`은 `03 FB FB FB`를 보내고 입력 버퍼 `[2],[3],[4]`를 각각 키 수, 노브 수, 스타일/버전 값으로 저장한다 (`0x10003df2e–df61`). WebHID에서 ID를 제거한 입력의 해당 위치는 `[1],[2],[3]`이다. 정적 코드에서는 스타일 값 **10 이상**이면 `_PHY2_KEY_Value`, 그 미만이면 `_PHY_KEY_Value`를 사용한다. 실제 응답 길이와 헤더를 확인한 뒤 이 분기를 적용해야 한다.

| 항목 | 새 계열: 스타일 >=10 | 구형 업체 FD50: 스타일 <10 |
| --- | --- | --- |
| 앱 내 저장 stride | 65 bytes | 65 bytes |
| 실제 쓰기에서 복사 | rec 64 bytes | rec 50 bytes + 0 패딩 |
| hidapi 전송 길이 | report ID 포함 65 | report ID 포함 65 |
| 설정 opcode | FD | FD |
| rec 헤더 | `[0]=FD,[1]=ID,[2]=layer` | 동일 |
| 모드 | rec[3] / wire[4] | 동일 |
| 키 개수 | rec[5] / wire[6] | rec[9] / wire[10] |
| 일반 키 | rec[8+3n] / wire[9+3n] | rec[11+2n] / wire[12+2n] |
| 보조키 | F1–F8의 별도 엔트리 | rec[10+2n] / wire[11+2n]의 HID 비트마스크 |
| 레이어 읽기 | `03 FA count 00 layer` | `03 FA keys knobs layer` |
| 레이어당 반환 수 | count | keys + 3×knobs |
| read에서 복사 | 입력[2..60] → rec[1..59] | 입력[2..50] → rec[1..49] |
| 커밋 | `03 FD FE FF` | `03 FD FE FF` 후 1초 대기 |

**헤더 근거:** 실제 동적 선택 함수의 새 경로 `0x100048ace–48ad7`, 구 경로 `0x100049035–4903e`가 FD/ID/layer를 저장한다. `0x1000083f2` 주변에는 오래된 stride50 콜백도 남아 있지만 현행 setter/read/write 저장 stride는 65이다. 이 두 주소군을 혼합해 배열 주소를 계산하면 안 된다.

**쓰기 근거:** `HID_write() @0x10003d590`; 새 경로 `d694–d6c7`는 64바이트를 report ID 뒤에 복사한다. 구 경로 `d7ae–d7ef`는 50바이트를 복사한다. 구 커밋은 `d8e7–d92b`. `hid_write()` 성공은 장치 적용 성공이나 비휘발성 저장 검증이 아니다.

**읽기 근거:** `read_Hidkey_Data(unsigned char layers,unsigned char keys,unsigned char knobs) @0x10003e610`. 새 요청은 `e666,e672,e681,e714`, 새 반환 복사는 `e7f0–e855`. 구 요청은 `e871–e877`; 일반키 루프는 `e943–ea8b`, 노브 루프는 `ea9e–ebe7`. 기존 함수는 반환 헤더·짧은 응답·중복/누락을 엄격히 검증하지 않으므로 그대로 복제하면 안전한 백업이 아니다.

함수 자체는 count를 받지만 발견한 호출자는 새 계열에서 `(3,25,0)`, 구형에서 `(3,15,3)`을 사용한다 (`0x10003e4a5–e4e5`, `0x100035043–35147`). 새 모델에서 `keys+3×knobs`를 요청하는 확장은 응답으로 검증할 구현 가정이며, 이 원본의 호출 동작으로 입증된 값은 아니다.

## 구형 키·미디어·마우스 코덱 후보

이 절은 **오프라인 구현 가능한 계약 후보**다. 구형 실물의 설정/복원 검증은 아직 없다.

- 키: `SetBasicKey() @0x1000464bd–64d8`가 rec[9]를 읽고 rec[11+2n]에 HID usage를 넣고 count를 1 증가시킨다. `SetFunKey() @0x100046646–666d`는 같은 슬롯 rec[10+2n]에 modifier를 OR한다. 비트는 Ctrl/Shift/Alt/Meta/오른쪽 변형 순서의 `01,02,04,08,10,20,40,80`이다. 새 계열의 F1–F8 특수 코드를 여기에 넣으면 안 된다.
- 미디어: `SetMulKey() @0x100046c6e–6ca3`는 rec[10+2n], rec[11+2n]에 테이블의 두 바이트를 넣고 **count를 2 증가**시킨다. 처음 빈 레코드면 Consumer usage LE가 rec[10],rec[11]에 들어가고 rec[9]=2가 된다. 아래 공개 구현은 count0 또는 count1을 사용하므로 서로 같다고 처리하지 않는다. 정상적인 실제 원본 레코드를 보존하고 종류별 count를 엄격히 구분해야 한다.
- 마우스: `SetMousePage() @0x100046ed0`의 구 경로는 rec[10] modifier, rec[11] 버튼, rec[14] 휠을 사용한다. 버튼 1/2/4는 `0x100046f9c / 4702c / 46ff1`; 휠 +1/-1은 `0x100047067 / 47210`; count=1은 `0x100047231`; mode는 rec[3]에 저장한다. 이동·드래그·수정키가 섞인 미지원 레코드는 원문 보존이 필요하다.

슬롯 개수의 최대값과 전송 보존은 별도다. 공개 구형 코드는 18쌍을 지원하지만 현재 프로필의 14입력 제한을 늘릴 근거로 사용하지 않는다. 이 문서는 지연·LED·DFU·모델 식별값 변경의 구현을 승인하거나 권장하지 않는다.

## 구형 노브 ID

구형 읽기 루프는 **ID 16부터** 노브 결과를 저장한다 (`0x10003ea9e`), 일반키 바로 다음 `keys+1`부터가 아니다. 3키/1노브여도 노브 기본 주소를 4로 만들면 안 된다. 구형 저장 인덱스는 action ID를 직접 사용하므로 여기서 16은 wire ID16이다. 새 16키/3노브의 노브 17–25와 혼동하지 않는다.

공개 소스의 구형 주소 후보는 노브 k(0부터) → `16+3k+action`이며 12키/4노브는 네 번째 노브를 **13–15로 재사용**한다. 12+4는 25–27을 보내는 방식이 아니다. 회전 방향의 실제 순서는 공개 구현끼리 설명이 달라 물리 입력으로 확인해야 한다. 이 매핑은 미검증 카탈로그에 저장할 수 있지만 연결된 모델의 검증 완료를 뜻하지 않는다.

## 공개 구현의 일치·불일치

[whatabeautifulmemory/webhid-minikeyboard-setup 소스](https://github.com/whatabeautifulmemory/webhid-minikeyboard-setup/blob/dfdd1ce27ea26fdc8ae73fd9c3589a160b148180/index.html)의 `REC`, `CMD`, `buildRecord`, `parseRecord`, `readAll`, `writeAll`을 확인했다. 구형 FD50 필드와 읽기/커밋을 구현하며 항상 `FA 0F 03 layer`로 24개를 수집한다. 프로젝트 작성자는 `514c:8850` 3키/1노브 읽기 실기를 보고하되 쓰기 실기 미검증을 명시한다. 원본 바이트 전체 보존 없이 해석 객체로 재구축하고, 되읽은 결과를 기대 바이트와 비교하지 않아 이 프로젝트의 엄격한 백업/검증 계약을 대신하지 못한다. 특히 media count=1이다. [설명과 실기 범위](https://github.com/whatabeautifulmemory/webhid-minikeyboard-setup)

[ch57x-keyboard-tool 고정 소스: k884x.rs](https://github.com/kriomant/ch57x-keyboard-tool/blob/bdbffca368f2084fbd111bc64463b881cd7c8fee/src/keyboard/k884x.rs)는 **FE** 설정 opcode, media count=0, commit 전후 AA AA 메시지를 사용한다. 업체 앱의 FD50와 다르므로 그대로 이식하지 않는다. 12+4의 13–15 재사용은 `to_key_id`에 있다. [k8850_4x4.rs](https://github.com/kriomant/ch57x-keyboard-tool/blob/bdbffca368f2084fbd111bc64463b881cd7c8fee/src/keyboard/k8850_4x4.rs)는 FD와 3바이트 엔트리/독립 modifier를 사용하여 새 계열을 뒷받침하지만 역시 쓰기 생성 코드이며, 읽기/백업 검증 근거로 승격할 수 없다. `1189:8890`은 별도 프로토콜이며 자동 호환 대상으로 넣지 않는다.

## 구현을 진행할 수 있는 범위

1. **카탈로그/검색:** 장치 후보를 넓게 노출하되 VID:PID를 코덱 결정으로 사용하지 않는다. 컬렉션·report descriptor·FB 헤더/정확한 응답 길이·스타일을 함께 확인한다.
2. **읽기/백업:** dialect별 요청/반환 수/ID 집합을 사용한다. raw input 전체와 FD 설정용 정규화 레코드를 구분해 저장한다. 레이어와 ID의 중복·누락·범위·응답 길이를 검증하고, 모든 레이어의 원본을 확보하기 전 쓰기를 열지 않는다. 구형 노브 ID13–24를 포함할 수 있는 전체 반환을 보존한다.
3. **오프라인 코덱:** 새 계열과 구형 FD50을 분리하고 미지원 바이트를 보존한다. 구형 media count 충돌과 회전 방향은 미검증 필드로 남긴다. FE k884x는 세 번째 별도 경로로만 다룬다.
4. **실물 검증:** 해당 dialect/model의 원래 레코드를 저장한 뒤, 사용자 승인 범위에서 한 슬롯 변경 → 전체 독립 되읽기 → 기대 변경 비교 → 원본 복원 → 전체 되읽기 일치로 승격한다. 이 조사에서는 실시하지 않았다.

프로젝트의 [기존 물리 canary](../evidence/physical-canary.json)는 identity `[16,3,11]`, action25/layer3의 변경·복원 검증만 기록한다. 다른 개수·구형 FD50·FE 모델로 이 결과를 확장할 수 없다. LED 상태를 포함하지 않는 키 설정 백업은 펌웨어/장치 전체 이미지가 아니다. 따라서 **구형 FD50 코덱의 보수적인 오프라인 구현과 읽기/백업 연결은 가능하지만, 현재 근거만으로 구형 쓰기를 검증 완료로 표시할 수 없다.**
