# LED visible-effect investigation — 2026-10-25

Status: stored values and visible activation are distinct; color writes are verified, mode activation timing remains partially characterized.

- Device: 514c:8850, identity [16,3,11]. All key records backed up before trials.
- User observed continuously lit LEDs for stored layer-1 mode values 0..5. No semantic mode names can be established from this result.
- All three layers were temporarily written mode 1 / red in every slot. Reads returned the requested values, but user saw no color change.
- A later known key commit sequence AA AA / FD FE FF / AA AA preserved the immediate 75-key snapshot and all raw LED replies. User still saw no color change. A missing commit alone is not established as the cause.
- Intermediate reads showed user key and color edits since the earlier backup. Stale-baseline assertions stopped before commit; subsequent comparison used a new immediate snapshot. Do not restore old keys over these edits.
- Original vendor binary SHA-256 remains 6f330a43fc9493d8f76e112b08c054d7c896a0d628d2e41bbfd701dbedfd6f4f. Native static inspection shows matching FE B0 layer0..2 mode RGB48 layout. Its post-LED commit is conditional on key changes; adding it as an unconditional fix is unsupported.
- Native model/UI gating also routes style11 to the new RGB path. Generic mode/color controls do not establish physical LED support on this firmware. Do not send legacy packed LED records or model-selection commands as speculative fixes.
- Companion was closed with verified temporary LED restoration before launching the original MINI_KEYBOARD app. Vendor UI read the stored red/yellow palette and mode1. The original app selected mode4 and reported Saved successfully. After quitting the vendor app and reopening the companion, reads returned modes [4,0,0]; key records matched the pre-vendor snapshot exactly. A blue swatch click did not alter the read color data, so this is a mode-save comparison only.
- User confirmed the vendor-saved mode4 changed the visible lighting only after USB unplug/replug. After reconnect, all raw LED responses matched the vendor-saved snapshot and all 75 key records matched. The reported mode4 appearance was violet at bottom-right through red at top-left, with top-left three keys unlit; this does not establish a universal effect name.
- Using our combined apply path, wrote mode1 and blue in every slot of all three layers with all key actions preserved. User confirmed all keys became blue after USB reconnect; all raw LED and key records survived the reconnect exactly.
- Restored the exact LED records from led-activation-debug-original.json using persistent save, without restoring stale key records. The user's newer key edits were preserved. User then confirmed the restoration changed visible colors immediately WITHOUT reconnect. Thus a universal reconnect requirement for colors is disproven. The observed sequence is consistent with mode activation being latched until reconnect and same-active-mode colors updating live, but firmware internals and alternative activation triggers remain unknown.
- No speculative command/commit change is shipped. UI now separates saved/readback values from physical activation. Only a stored-mode change suggests reconnect conditionally if its visible effect does not change; color-only save does not demand reconnect. No numeric effect names are invented.
